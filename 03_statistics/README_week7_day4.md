# 第7周 Day4：A/B 测试综合业务决策

## 1. 今日学习目标

将数据质量、样本量、统计显著性、业务显著性和护栏指标放入同一个决策框架，形成从实验结果到上线建议的完整分析流程。

## 2. 完整决策流程

一次 A/B 测试不能只看转化率高低，应依次检查：

1. 数据质量与 SRM 是否正常。
2. 样本量和实验周期是否达到预设要求。
3. 核心指标是否达到统计显著。
4. 实际提升是否达到业务上值得关注的最低标准。
5. 退款率、错误率等护栏指标是否通过。
6. 全部通过后先灰度发布，并持续监控和保留回滚能力。

## 3. 统计显著与业务显著

统计显著回答：观察到的差异是否较难用随机波动解释。

业务显著回答：实际提升是否足够大，值得承担开发、运营和风险成本。

两者不能互相替代：

- 统计显著但业务价值不足，通常不值得上线。
- 业务提升看起来足够，但统计证据不足，需要继续实验。
- 两者都通过后，仍需检查护栏指标。

本次课程将两个字段明确区分：

- `statistical_mde = 0.01`：实验希望可靠检测出的 1 个百分点提升，用于样本量设计。
- `business_minimum_lift = 0.005`：业务上至少值得关注的 0.5 个百分点提升。

## 4. 当前实验结果

新版结算页实验结果：

- A组用户数：5,000
- B组用户数：5,100
- A组转化率：8%
- B组转化率：9%
- 绝对提升：1 个百分点
- p-value：0.0717
- 显著性水平：0.05
- 基准方案每组所需样本量：12,208
- 退款率增加：2.63 个百分点，允许上限为 1 个百分点
- 错误率增加：0.57 个百分点，允许上限为 0.2 个百分点
- 未发现 SRM 异常

## 5. 自动检查结果

| 检查项目 | 是否通过 | 解释 |
|---|---|---|
| 数据质量与 SRM | 是 | 暂未发现明显分流异常 |
| 样本量 | 否 | 两组都低于每组 12,208 人 |
| 统计显著性 | 否 | 0.0717 大于 0.05 |
| 业务显著性 | 是 | 1 个百分点高于业务最低要求 0.5 个百分点 |
| 退款率护栏 | 否 | 实际增幅超过预设上限 |
| 错误率护栏 | 否 | 实际增幅超过预设上限 |

失败原因包括：样本量不足、未达到统计显著、退款率护栏未通过、错误率护栏未通过。

## 6. 当前业务结论

本次实验暂未发现明显分流异常，B组样本转化率提高了 1 个百分点，观察到的提升具有潜在业务价值。但是样本量不足、核心指标未达到统计显著，而且退款率和错误率均超过预设护栏阈值。

因此，目前既不能宣布 B 组有效，也不能宣布 B 组无效，更不能直接全量上线。当前建议是暂停上线，优先调查和修复护栏指标异常；修复后重新实验，并继续积累至预设样本量，再结合核心指标、置信区间和护栏指标重新判断。

## 7. 不同场景的决策规则

| 场景 | 建议 |
|---|---|
| 所有条件通过 | 具备上线条件，先小流量灰度发布 |
| 样本量或统计证据不足 | 继续实验并积累样本 |
| 统计显著但业务价值不足 | 不建议上线 |
| 护栏指标未通过 | 暂停上线，调查并修复负面影响 |
| 数据质量或 SRM 异常 | 暂停效果分析，先检查分流、埋点和数据质量 |

数据质量具有最高优先级。如果数据或分流不可信，后续差异、置信区间和 p-value 都可能失去解释基础。

即使所有条件通过，也不应直接 100% 全量上线。更稳妥的方式是小流量灰度发布，持续监控核心指标和护栏指标，逐步扩大流量，并保留异常回滚能力。

## 8. 代码知识点

- 使用布尔条件自动判断各项实验标准是否通过。
- 使用 `&` 表示多个条件必须同时满足。
- 使用函数和 `DataFrame.apply(..., axis=1)`逐行生成失败原因与决策建议。
- 使用 `"；".join(list)`连接多个失败原因。
- 使用决策优先级避免在数据异常或护栏失败时给出错误的上线建议。
